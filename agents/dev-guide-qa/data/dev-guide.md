# 사내 개발 가이드 (데모용 발췌)

## 1. 배포 규정
- 운영 배포 창: 평일 10:00~16:00 KST. 금요일 15:00 이후와 공휴일 전날은 배포 금지.
- 모든 운영 배포는 카나리(5% → 50% → 100%)로 올리고, 단계마다 10분 이상 오류율·지연을 확인한다.
- 배포는 파이프라인(CI)만 수행한다. 사람이 직접 운영 서버에 접속해 올리지 않는다.
- 되돌리기(rollback) 절차를 PR 설명에 적지 않은 변경은 배포할 수 없다.
- 데이터베이스 스키마 변경은 별도 PR 로 먼저 배포하고, 코드 변경은 그 다음 배포한다(확장 → 전환 → 축소).

## 2. PR 규정
- 리뷰어 2명 승인이 필요하고, 그중 1명은 해당 서비스의 소유 팀이어야 한다.
- 변경 줄 수가 400줄을 넘으면 PR 을 나눈다.
- 테스트: 단위 테스트는 필수, 외부 API 를 부르는 코드는 계약 테스트(contract test)를 추가한다.
- PR 설명 항목: 목적, 변경 요약, 위험, 되돌리기 방법, 모니터링 지표.
- CI 가 녹색이 아니면 머지하지 않는다. 플레이키 테스트는 재시도하지 말고 고친다.

## 3. 로그와 개인정보
- 로그에 개인정보(이름·이메일·전화·주소·결제 수단 번호)를 남기지 않는다. 필요하면 식별자(user_id)만 남긴다.
- 요청 본문 전체를 로그로 남기지 않는다. 필드 단위로 선택해 남기고, 마스킹 함수(`mask_pii`)를 거친다.
- 로그 보존 기간은 30일, 감사 로그는 1년이다.

## 4. 비밀값
- 비밀값(토큰·키·비밀번호)은 Vault 에만 둔다. 코드·설정 파일·환경 변수 파일(.env)에 넣지 않는다.
- 서비스 토큰은 90일마다 교체한다. 교체 절차는 플랫폼 팀 런북을 따른다.
- 로컬 개발에서도 운영 비밀값을 쓰지 않는다. 개발용 Vault 경로(`secret/dev/*`)를 쓴다.

## 5. 의존성
- 새 라이브러리는 사내 승인 목록(보안팀)에 있어야 한다. 없으면 보안팀에 검토를 요청한 뒤 쓴다.
- 라이선스: MIT·Apache-2.0·BSD 허용, GPL 계열은 금지(동적 링크 포함).
- 버전은 고정(pin)하고, 취약점 점검(CVE)은 CI 에서 자동으로 돈다. High 이상은 머지 차단.

## 6. 장애 대응
- 장애 감지 후 15분 안에 incident 채널에 첫 보고를 올린다(현상·영향 범위·담당자).
- 되돌리기가 가능하면 원인 분석보다 되돌리기를 먼저 한다.
- 장애 종료 후 3영업일 안에 사후 검토(postmortem) 문서를 쓴다. 책임 추궁 없이 원인과 재발 방지만 적는다.
